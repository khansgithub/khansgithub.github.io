## What is pkb?

this project is a web app to quickly find snippets i've saved about specific topics. i initially had a github markdown gist, where i added random snippets of information and referenced as a cheat sheet. the information was spread between the markdown file, and the comments on the gist. it started to become difficult to look up information, because many of the snippets were recorded as comments to the gist, and the web page doesn't load all the comments at once - only the latest few. this made it hard to ctrl-f and look up things i needed.

so this personal knowledge base idea was born. there were a few difficult aspects to this that i wanted to explore, using this project:
	- parsing of semi structured data
		- the structure of how i made the initial markdown file mostly stayed consistent, but the format of how the snippets in the comments were structured varied a lot. consolidating it all into one data structure was a tricky step which required several iterations
	- storing + looking up data in postgres
		- i have very little experience with postgres, so i wanted to use this opportunity to use it more. learning about the different kinds of look ups, indexes and using supabase was very challenging but also rewarding
	- building a detailed UI
		- i'm not the greatest at UI and UX design, but i used this opportunity to explore tailwind more, and try experimenting with designing the web application

the app itself is deliberately minimal - it's one search box, and results appear as you type.

## Stack

- **Frontend:** SvelteKit, TypeScript, Tailwind, daisyUI
- **Backend:** SvelteKit server routes, Supabase (Postgres)
- **Search:** Postgres full text search (`tsvector`) + trigram similarity (`pg_trgm`), GIN indexes
- **Parsing:** Python, gist markdown + comments → structured snippet data → CSV → imported into Postgres
- **Caching:** Dexie (IndexedDB), in the browser
- **Testing:** Vitest, MSW, Playwright
- **Deploy:** Vercel

## Features

- modelling of messy unstructured data
- does fuzzy search on the snippets, searching across content + tags
- fast look ups with browser caching
- minimal interface so it's easy to search and get results
- full text and trigram search run together, then deduped by snippet id, so a partial or misspelled query still matches
- code blocks keep their language, and are syntax highlighted when expanded
- results are cached against the query string, so a repeated search doesn't hit the database again
- a sync endpoint that clears the cache and rebuilds the index from the gist

## Search

the search is the part i spent the most time on. there are two tables - `snippets` holds the title, tags and description, and `blocks` holds the actual content, typed as either `code` or `text`, with the language and the lines for each one. a snippet is a row in `snippets` plus the ordered blocks that belong to it.

four queries run against that data:

- `snippets_fts_query` - full text search over the snippet text and path
- `snippets_trgm_query` - trigram similarity over the same
- `blocks_fts_query` - full text search over the code block contents
- `blocks_trgm_query` - trigram similarity over the code block contents

they're unioned together in a `full_search` postgres function, and deduped with `DISTINCT ON (id)` so a snippet matching in several ways only shows up once.

both search types are backed by GIN indexes. the tricky part was that postgres won't use an index on an expression that isn't immutable, so `array_to_string` needed wrapping in an `array_to_string_immut` function before the `to_tsvector` and trigram indexes would get used.
